# 智能制谱内容框架与执行方案

> 2026-08-20 · 依据产品负责人手绘流程图整理 · 状态：**三项已拍板**（见第九节）· A1 已随 v60.14 上线

---

## 一、草图识读

手绘图的流程（六个节点）：

```
音频（文件或链接）
   ├─ 转MIDI ─→ ① MIDI 主旋律 ──┐
   ├─────────→ ② 和弦识别   ──┴─→ 直接出谱
   └─────────→ ③ 音轨识别（优先吉他 / 钢琴 / 尤克里里）
                     │
                     ↓（无法识别时走这条）
              ④ 自动编配和弦（专业级自动配和弦）
                     ↓
              ⑤ 预设节奏型（专业级·不同风格）
                     ↓
              ⑥ 成品谱
```

**这张图的核心判断是对的，而且它其实画的是两条路**：

- **识别成功 → 直接出谱**：音频里本来就有的信息，尽量原样还原（①②③）
- **识别失败 → 自动生成**：识别不出来的部分，用规则和内容库补出一份**能弹的**（④⑤）

产品负责人另外明确了边界：**①②③（音频转 MIDI / 扒原版伴奏）难度太大，交给上游**；
护城河建在 **④⑤** —— 分难度等级的自动配和弦 + 海量不同风格的节奏型。

这个切分是成立的，理由见第六节。

## 二、家底核对（先看已有什么，别重做）

盘完代码，**草图的 ④⑤⑥ 已有雏形，①②③ 有部分入口**：

| 草图节点 | 现状 | 缺口 |
|---|---|---|
| ① MIDI 主旋律 | **已有** MIDI 导入（`.mid/.midi`）、哼唱成谱（`hummingToSong`）、GP/MusicXML 导入 | 音频→MIDI 本身没有 |
| ② 和弦识别 | 音频侧**无**；但有「一键配和弦」（功能和声打分：强拍加权 / 根音加权 / 首尾偏主和弦） | 从音频识别和弦 |
| ③ 音轨识别 | GP 导入有音轨选择；音频分轨**无** | 音频分轨 |
| ④ 自动编配和弦 | **已有**「一键配和弦」+「一键配伴奏」（旋律→和弦→双手织体） | **无难度概念** |
| ⑤ 预设节奏型 | **已有** 吉他节奏型 **60 条 / 9 类**；钢琴织体 **11 套** | 见下 |
| ⑥ 成品谱 | **已有** 八场景 docType + 三记谱法同源互切 + 出版级刻版 | — |

**⑤ 的真实状态（关键）**：

- 吉他 60 条节奏型：分类是**按拍号和演奏法**（分解 / 扫弦 / 半小节 / 一拍 / 基础时值 / 组合 / 3-4 拍），
  条目只有 `{name, span, ev}` —— **没有风格标签，也没有难度标签**
- 钢琴 11 套织体：**已有 `level:'入门' / '进阶'`** —— 这是全站**唯一**有难度概念的地方

**所以真正缺的不是功能，是体系**：难度模型、风格分类、以及「可切换」所需的架构。

另一个有利条件：和弦指法库 `CHORD_SHAPES` 用 `'x32010'` 这种逐弦编码存（`x`=不弹，base36 品位），
意味着**横按 / 跨品 / 把位 / 空弦数全部可以直接算出来** —— 难度模型可以建立在真实数据上，不靠拍脑袋。

## 三、核心架构决策：骨架 / 编配层分离

**这是整个方案的地基，也是必须现在定的一件事**——数据模型定错，后面「随意切换」做不出来，返工代价极大。

把一份谱拆成两层：

**骨架 Skeleton（自动流程不得改写）**
- 旋律音高与时值
- 和弦进行（和弦名序列，不含具体指法）
- 曲式结构（段落、反复、房子）
- 调号 / 拍号 / 速度 / 歌词

**编配层 Arrangement（可重算、可切换、可丢弃）**
- 节奏型 / 织体的具体音符
- 和弦的具体指法、转位、把位
- 加花、经过音、力度型

编配层由一个**描述符**决定，生成过程确定性（同描述符 → 同结果）：

```js
arr = { style:'folk', level:3, instr:'guitar', variant:0 }
```

**切换 = 换描述符重算，骨架原样不动。**

配套两条规则：
1. **用户手改过的小节打 `locked` 标记，重算永不覆盖** —— 沿用现有「已有和弦的小节绝不覆盖」的既有原则，扩展到编配层
2. 字段**只增不改**（`arr` / `locked` 都是新键），符合数据红线

> 现状的「一键配伴奏」是**破坏性**的（生成后替换当前窗口）。这一层不做，
> 「不同风格不同难度随意切换」就只能是「重新生成一遍并丢掉用户的修改」，产品上站不住。

## 四、内容框架

### 4.1 难度分级 L1–L5（判据可计算，不靠主观）

每一级都给**能从数据算出来的判据**，标注对不对可以被脚本校验：

| 级 | 名称 | 和弦判据 | 节奏判据 |
|---|---|---|---|
| L1 | 入门 | 仅开放和弦（无横按）；每小节 ≤1 次转换 | 仅四分 / 八分；无切音 |
| L2 | 初级 | + 小横按（≤3 弦同品）；每小节 ≤2 次转换 | + 八分分解；简单切分 |
| L3 | 中级 | + 大横按（≥4 弦同品）；+ 转位低音 | + 十六分；切音 / 闷音 |
| L4 | 高级 | + 七 / 九和弦；把位移动 ≥3 品 | + 复合切分；双音加花 |
| L5 | 专业 | + 代理和弦；经过和弦 | + 打板；复杂切分 |

**可计算的判据来源**（全部来自现有数据结构）：

| 指标 | 算法 |
|---|---|
| 横按度 | `CHORD_SHAPES` 里最低非零品在 ≥2 根弦上同品 → 横按；同品弦数即宽度 |
| 跨品 | 非零品位的 `max − min` |
| 把位 | 最低非零品位 |
| 空弦数 | 值为 `0` 的弦数（越多越易） |
| 节奏密度 | 节奏型 `ev` 里的最小时值 |
| 转换频率 | 每小节和弦数 |

### 4.2 风格分类学（三维正交）

- **风格大类**：民谣 / 流行 / 摇滚 / 布鲁斯 / 乡村 / 拉丁（Bossa·Rumba）/ 爵士 / 儿歌 / 古风 / 赞美诗
- **拍号族**：2-4 拍 / 3-6 拍 / 复合拍
- **演奏法**：分解 / 扫弦 / 半分解 / 柱式 / 琶音 / 切音

一条节奏型可以同时属于多个风格（如「53231323 经典分解」既是民谣也是儿歌）。

### 4.3 节奏型 / 织体元数据 schema

给现有 60 条 + 11 套**补齐**，新增条目按此录入：

```js
{ id, name, ev, span,               // 已有
  style: ['folk','pop'],            // 新增：风格标签（多值）
  level: 2,                         // 新增：难度 1–5
  meter: '4/4',                     // 新增：拍号族
  technique: 'arpeggio',            // 新增：演奏法
  instr: ['guitar','uku'],          // 新增：适用乐器
  bpmRange: [60, 110] }             // 新增：推荐速度区间
```

### 4.4 编配规则层（难度感知）

不只是「挑一条节奏型」，而是**整套编配按难度降级/升级**：

- **和弦简化表**：`Bm7♭5 → Bm`（L≤2）、`F → Fmaj7 小横按`（L≤2）、`C#m → 变调夹方案`（L1）
- **转位与低音行走**：L≥3 才启用
- **加花密度曲线**：L1 一小节一个音型，L5 逐拍变化
- **变调夹建议**：L1–L2 优先给出「夹几品可全用开放和弦」的方案

### 4.5 一键切换的产品形态

- 「**风格 × 难度**」二维选择器，选中即预览（不落库）
- 同一首谱可保存多套编配方案，支持 A/B 对比
- 手改过的小节显示锁标，重算时保留

## 五、执行方案（分期，每期可验收）

### P0 地基 · 2 个版本

| 编号 | 内容 | 验收 |
|---|---|---|
| P0-1 | `arr` 描述符 + `locked` 标记进 song 数据模型（只增字段） | 往返存取不丢字段；老谱打开不报错 |

### P1 难度引擎 · 2–3 个版本

| 编号 | 内容 | 验收 |
|---|---|---|
| P1-1 | 难度判据函数 + 和弦简化表 | 同一进行在 L1/L3/L5 产出可弹性明显不同，且和声功能不变 |

### P2 内容扩容 · 持续

- 节奏型 **60 → 200+**，按风格补齐（民谣/流行/儿歌先行）
- 每条入库必须过 P0-3 的自检
- 织体 11 → 30+，覆盖钢琴弹唱与考编常用

### P3 音频侧 · 交给上游

**我们的边界**：不自研 audio→MIDI / 音频分轨，只做「**上游产物 → 干净可弹谱面**」的最后一公里。

已有的落地能力（可直接承接上游产物）：MIDI 导入、MusicXML 导入、GP 导入、量化、调性判定、跨小节连音线处理。

**上游选型判据**（按重要性排序）：
1. 能否私有化 / 离线部署（数据出境与成本可控）
2. 是否同时输出**和弦与节拍**（只出音符的价值大打折扣）
3. 中文歌曲与国内乐器的实测准确率
4. 按次成本与并发上限

## 六、为什么这是护城河

**转谱本身正在商品化。** 模型每半年更新一次，上游会把 audio→MIDI 做到白菜价——
在那条赛道上自研，是拿有限资源去追一条注定被摊平的曲线。

而「**分难度 × 分风格 × 可切换**」需要四样东西同时具备：

| 能力 | 我们 | 纯模型公司 | 纯内容公司 |
|---|---|---|---|
| 出版级刻版引擎 | ✅ 已有 | ❌ | ❌ |
| 三记谱法同源互切 | ✅ 已有 | ❌ | ❌ |
| 大量人工标注的节奏型库 | ⚠️ 60 条，待扩 | ❌ | ✅ |
| 可判定的难度模型 | ⚠️ 待建 | ❌ | ❌ |

这是**内容 × 工程**的复合壁垒：纯模型公司出不了能弹的谱面，纯内容公司做不出可切换的引擎。
而且节奏型库是**越用越厚**的资产——用户的编配选择反过来能标注哪些组合好用。

## 八、编配质量专项：把 ④⑤ 做到专业水准

> 2026-08-20 追加。产品负责人反馈「自动编配和弦和节奏型库非常低级、错误百出」。
> 先用脚本把「错误」坐实，再给方案。审计工具已入库：`python3 deploy/arr-audit.py`

### 8.1 审计结论：错误是真的，但性质和预期不同

**先说一件必须交代的事**：审计脚本初版报出 3 条「硬错误」，
核对原始数据后发现**全是脚本自己的漏读**——附点写作 `[4,1]`（时值+附点位），
而初版正则只认单元素 `[dur]`，于是把「附点四分+八分×2」算成 1 拍、「附点二分」算成 0 拍。
修正后这三条各自是 4、4、3 拍，**完全正确**。
（同一支脚本还因为 `partial:true` 插在中间漏掉 2 个分类、因为只认 `ev` 不认 `durs` 让 3 类报 0 条。
审计工具本身不可信，它的结论就是噪音。）

修正后的真实结论：

| 对象 | 可复算的硬错误 | 真正的问题 |
|---|---|---|
| 节奏型库 | **0 条** —— 拍数、休止声明、重复、低音交替全部自洽 | **量太小 + 无风格无难度** |
| 配和弦 | 4 类结构性缺陷（见 8.3） | **小调系统性配错** |

**节奏型库覆盖度实测**（按拍号族 × 演奏法）：

| | 分解 | 扫弦 | 纯时值 | 片段 |
|---|---|---|---|---|
| 2/4·4/4 | 8 | 12 | 12 | — |
| 3/4·6/8 | 4 | 6 | 5 | — |
| 片段 | — | — | — | 13 |

**完整小节的可选型：4/4 只有 20 条、3/4 只有 10 条**，且 60/60 条无风格标签、无难度标签。
所谓「海量不同风格」，现状连**一个风格维度都不存在**。

所以「低级」这个评价是准的，但成因是**覆盖度与组织方式**，不是数据写错了。

### 8.2 配和弦：四类结构性缺陷

现有算法其实不弱——功能和声 Viterbi（发射分=旋律契合，转移分=功能进行），
还带副属和弦离调。问题在四处：

| 编号 | 缺陷 | 后果 |
|---|---|---|
| **C1** | 候选集**只有大调级数** I/IV/V/V7/vi/ii/iii；代码注释自己写着 `TODO: 小调` | **小调歌曲被配上大调和弦**——这是「错误百出」最主要的来源 |
| C2 | 缺 sus4/sus2、add9、vii°、m7b5 | 配不出民谣挂留、流行加九等常规色彩 |
| C3 | 和声节奏写死每小节一个（仅 4/4 下半段另属时补第二个） | 一小节两换、切分换和弦都做不到 |
| C4 | Viterbi 在全曲均匀跑，**不认乐句边界** | 配不出「前句半终止、后句全终止」的基本句法 |

### 8.3 配和弦执行方案

| 编号 | 内容 | 为什么排这个序 |
|---|---|---|
| **A1** | **小调 / 调式候选集** —— i、ii°/iiø、III、iv、v/V、VI、♭VII/VII；和声小调的大三属与自然小调的小三属按语境择一；调性判定扩展为大小调判别（末音/首音 + ♭3 与 ♮3 出现频次） | 影响面最大、错得最明显，**必须第一个做** |
| **A2** | **终止式模板** —— 正格 V-I、变格 IV-I、半终止 →V、阻碍 V-vi。做成 Viterbi 转移分上的**位置感知奖励**，而不是像现在只在末小节把 I 乘 1.6 | 句法是「专业感」的直接来源 |
| **A3** | **乐句结构感知** —— 先按 4/8 小节 + 长音 / 休止 / 歌词标点切句，再在句边界施加 A2 的偏好 | A2 的前提 |
| **A4** | **和声节奏可变** —— 强拍非和弦音且时值长时考虑换和弦；提供 每小节 1 / 2 / 按拍 三档，随难度联动 | 与难度分级天然咬合 |
| **A5** | **和弦类型扩容** —— sus / add9 / 6 / vii° / m7b5，每类附「何时用」的触发条件（不是全量丢进候选，否则 Viterbi 会乱选） | 有了 A1–A4 的骨架才不会失控 |
| **A6** | **风格化和声词典** —— 每个风格一套转移矩阵与候选权重：儿歌只用 I/IV/V 绝不离调；民谣加权 I-V-vi-IV；流行放开 ♭VII；爵士走 ii-V 链 | 直接支撑「按风格切换」 |

### 8.4 评测集：让「专业水准」可被证明

**这一条是整个第八节的关键，没有它，上面六条都只是换一批参数。**

- 建 **30–50 首标准答案曲目**（公有领域民歌 / 儿歌 + 自制片段），人工标注正确和弦
- 指标两个：**和弦级数准确率**（配得对不对）与**功能准确率**（T/S/D 对不对——
  配成 vi 而标准答案是 I，级数错但功能对，听感可接受）
- 每次改动跑一遍，纳入发版流水线
- **大小调分别统计**，防止大调涨分掩盖小调仍然错

没有评测集，「达到专业水准」无法验收，只能靠人耳抽查——这正是现在的状态。

### 8.5 节奏型库执行方案

| 编号 | 内容 | 验收 |
|---|---|---|
| **B1** | 补齐 `style/level/meter/technique` 元数据（即 P0-2） | `arr-audit.py` 元数据缺口归零 |
| **B2** | 扩容到 **200+**：按「风格 × 拍号 × 难度」建网格，每格 ≥3 条 | 网格无空格；民谣/流行/儿歌先满 |
| **B3** | 入库质量闸：必须过 `arr-audit.py`（拍数 / 重复 / 元数据）+ 人工试听 | CI 拦截不合格条目 |
| **B4** | **风格包**：把节奏型组织成可整体切换的包 | 一键切风格即换整套型 |
| **B5** | **变奏引擎**：同一型按难度自动加花 / 减花，而非每个难度手写一条 | 60 条 × 5 级不需要写 300 条 |

> B5 是控制内容成本的关键：手写 200 条已经很重，若再乘难度就不可持续。
> 正确做法是**写骨干型 + 规则化变奏**。

### 8.6 与护城河的关系

第六节说护城河是「内容 × 工程」的复合壁垒。第八节把它落到两件具体事上：

- **A7 评测集**是工程壁垒——有了它，配和弦的每次改进都可累积、可回归；
  没有它，任何人（包括我们自己）都说不清改好了还是改坏了
- **B2 + B5** 是内容壁垒——骨干型是人工资产，变奏引擎让它按难度自动展开，
  两者相乘才是「海量」

**排期建议**：A1（小调）优先级高于本文件第五节的全部 P1 内容——
小调配错是**用户能立刻听出来的错**，而难度分级是锦上添花。
建议顺序调整为：**A1 → P0 地基 → A2/A3 → P1 难度引擎 → A4–A6 与 B 系列并行**。

### 9.1 产品负责人已拍板三项

| 事项 | 结论 |

### 9.2 开源家底调研结论（一句话：和弦侧有可用件，节奏侧没有）

调研范围：可嵌入浏览器单文件的引擎 / 可复用的乐理数据 / 可作评测集的语料 / 节奏型语料。

**A. 配和弦——有三样可用，但都不是「拿来即用的引擎」**

| 资产 | 许可 | 能拿来做什么 | 为什么不能直接当引擎 |
|---|---|---|---|
| **tonal**（tonaljs/tonal） | MIT · 零依赖 · 有浏览器 UMD 包 | `Key.minorKey()` 直接给出自然 / 和声 / 旋律小调的级数、三和弦、七和弦、功能标记与副属和弦——**A1 的权威对照表** | 它只是**乐理查表**，不含「旋律→和弦」的决策 |
| **note-seq `chord_inference.py`**（Magenta） | Apache-2.0 | 算法参考：把**调性与和弦联合**放进 Viterbi、带转调惩罚、每小节 2 个和弦位——正是 A3/A4 要做的事 | Python，且面向 MIDI 多声部；须移植而非引用 |
| **Chordonomicon**（66.6 万首和弦进行 + 曲风标签） | 仓库 Apache-2.0 | A6 风格词典的**统计来源**：按曲风回归转移矩阵 | 数据自用户上传的和弦谱抓取而来，**只可取聚合统计，不可分发原始进行** |

深度学习类（AutoHarmonizer、MTHarmonizer、DeepChoir 等）均为 Python + TensorFlow 训练产物，
**与「单文件、无构建、浏览器内运行」的硬约束冲突**，只能作为将来服务端功能评估，本轮不采纳。

**B. 节奏型库——没有可用的开源资产，B 系列按原方案自研**

| 候选 | 许可 | 判定 |
|---|---|---|
| MMA（Musical MIDI Accompaniment）groove 库 | GPL（社区包 Artistic-2.0 / GPL-2+） | **不可嵌入**闭源单文件产品；其**风格分类**可作覆盖度对照清单（分类法是事实，不受版权保护） |
| Groove MIDI Dataset（Magenta） | CC-BY-4.0 | 许可可用，但**只有鼓**，与吉他扫弦 / 分解无关 |
| Fraunhofer IDMT Guitar | CC BY-**NC-ND** | 禁商用 + 禁演绎，**完全不可用** |
| DadaGP（26k Guitar Pro 曲目） | 仅限研究 | 源自受版权保护的扒谱，**不可用** |

> 结论：**世界上不存在一份许可干净、机器可读的吉他节奏型语料**。
> 这既是坏消息（B2 的 200+ 条得自己写），也是好消息——
> **它恰恰说明这块内容资产为什么能构成壁垒**：谁都拿不到现成的。

## 十、A8 进行模板层（固定级数走向 / 套路）— 已随 v60.15 上线

### 10.1 为什么原方案漏了它

产品负责人提问：「和弦进行套路（固定级数走向）有没有规划？是不是优先匹配固定走向？」
核对结论：**没有，而且原结构做不到**。

- 转移分是**一阶**的（只看相邻两个和弦）：`1-5-6-4` 与 `1-5-6-3` 的差别只体现在其中一个转移分上，
  引擎里不存在「整条走向」这个概念
- 套路的旋转变体（`5-6-4-1` / `6-4-1-5`）无法被识别成同一件事
- 没有循环/段落意识：同一段旋律出现两遍，不保证配出同一套和弦
- 第 8 节的 **A2 只是两个和弦**的收束式，**A6 只是换一张一阶转移矩阵**——都不等于套路

代码里出现的「卡农」「4536」在 `index.html` 的**预设示范曲**里，是内容不是能力。

### 10.2 落地设计

| 层 | 做法 |
|---|---|
| **A3 乐句切分** | 证据 = 小节末长音 / 末尾休止 / 歌词标点 / 4 小节格；小 DP 切成 2–8 小节的句（偏好 4） |
| **A8 模板库** | 12 条（大调 7 + 小调 5），每条 = 级数序列 + 是否允许旋转 + 权重；**每格是一组候选**（如 V / V7 同格） |
| **匹配** | 以乐句为跨度枚举「模板 × 旋转 × 铺排」，用**同一套发射分/转移分**打分 |
| **跨度合并** | 相邻两句可合并（≤8 小节）——否则 8 格卡农永远等不到 8 小节的段；再用小 DP 选覆盖 |
| **采纳阈值** | 套路仅带每小节 `PROG_PRIOR=0.30` 的先验，打不过自由最优就**退回自由解** |
| **终止式收尾** | 跨度含全曲末小节且**旋律收在主音**时，末格换主和弦 |
| **重复乐句** | 旋律指纹一致的句沿用先前决定 |

### 10.3 两个坑（都已写进代码注释，避免以后重犯）

1. **切分的累计偏置**：边界证据若取绝对值，段越多总分越高，DP 系统性偏向切碎——
   全曲每小节都以长音收尾时，8 小节被切成 4 段 2 小节。改为**减去全曲均值**后修正。
2. **终止式不能写成硬性护栏**：先写成「含末小节的套路必须收主和弦」，
   结果把一条正经的、旋律收在 `6` 上的 1-5-6-4 乐句毙掉了。判据应取**旋律末音**，不是小节序号。

### 10.4 实测对照（v60.15）

| 场景 | 无套路层 | A8 之后 |
|---|---|---|
| 含糊小节（只剩 `1`/`3`） | `C G C F` | `C G Am F`（命中 1-5-6-4） |
| 卡农型旋律 8 小节 | `C G Am C F C F C` | `C G Am Em F C F C`（三级归位 + 末小节收主） |
| 5 小节旋律 | `C C F G C` | `C Am F G C`（vi 覆盖 4/4 音，C 仅 3/4；命中 1-6-4-5） |
| 小调 8 小节 | `Am G F G Am G F Am` | 同上，但**标记出** i-♭VII-♭VI-♭VII |
| 旋律不合任何套路 | `G7…C` | `G7…C`（**一条套路都不套**） |

`tv_prog` 8 项；变异验证：清空模板表 → 5 项转红；切分退回绝对分 → T1 转红。53 套件全绿。

### 10.5 已知边界（下一步）

- 套路目前**每格恒等于一小节**，与 A4（半小节换和弦）尚未打通
- 模板表已预留 `style` / `level` 字段，但还没接「风格 × 难度」选择器（P1）
- 套路命中率尚未纳入 A7 评测集指标（应与级数准确率**分开统计**，防止为命中率牺牲准确率）

**排期更新**：A3 与 A8 已完成 → 下一步 **A7 评测集** → A2 收束式（部分已被 A8 吸收）→ P1 难度引擎。

## 十一、A7 评测集（已随 v60.16 上线）

### 11.1 语料与标注口径

| 项 | 内容 |
|---|---|
| 规模 | 首批 **9 首 / 80 小节**（目标 30–50 首） |
| 构成 | 6 首公有领域传统曲目（小星星 / 两只老虎 / 欢乐颂 / 铃儿响叮当副歌 / 玛丽有只小羊羔 / 小蜜蜂）+ 3 段自制小调片段 |
| 标注形态 | **每小节一个「可接受和弦集合」**，不是唯一答案——配和弦本就多解，钉死单答案等于对某一种配法过拟合 |
| 标注来源 | 本项目自行标注（通行教学配法），**非第三方语料**，需产品负责人复核 |
| 自制片段规则 | 先定和声意图（进行）→ 再按和弦内音写旋律 → 写完即固定，**不得在看到引擎输出后回头改标注** |

### 11.2 指标与闸门

- **级数准确率**：产出和弦 ∈ 可接受集合
- **功能准确率**：T/S/D 与集合中任一答案一致（配成 vi 而答案是 I → 级数错、功能对，听感可接受）
- **套路命中率**：A8 覆盖的小节占比，**单独统计、不进闸门**——否则会为命中率牺牲准确率
- **大调 / 小调分桶**：防止大调涨分掩盖小调仍然错
- **结构性不变量**：凡旋律收在主音上的曲目，末小节必须配主和弦

当前成绩：级数 **97.5%**、功能 **97.5%**、小调 100%、套路命中 40%。

### 11.3 首轮跑分抓出的两处真缺陷（都已修）

| # | 缺陷 | 根因 |
|---|---|---|
| a | 小星星整首停在属和弦 | **重复乐句复用越过终止式**——m9–12 与 m1–4 逐音相同，复用把前句收在 V 的决定搬到末句；模板层本已算出收主和弦的版本（调试显示 `cad=true`）却被覆盖 |
| b | 欢乐颂整首停在属和弦 | **自由路径不认终止式**——末小节长音落在属和弦五音上，1.6 / 0.8 的主和弦偏置压不过 |

修法统一为「**判据取旋律末音**」：末音收主音时主和弦偏置 2.0 / 0.5（自由与模板同口径），复用路径对末句单独补收尾。
级数 93.8% → 97.5%，功能 96.3% → 97.5%。

### 11.4 闸门自身的缺陷（同轮发现并修）

初版地板留了 1.5% 余量。变异实测：**把终止式修复抽掉，成绩只掉到 96.3%，照样绿**——
80 小节的语料上一小节只占 1.25%，余量放大就等于没有闸门。两处改动：

1. 地板收紧到「**错一小节就红**」（97% / 97% / 100%）
2. 加**结构性不变量**断言（末音收主音 ⇒ 末小节配主和弦）——百分比对单小节回退不敏感，结构量敏感

三个变异体（只抽 a / 只抽 b / 两个都抽）现在全部转红；其中「只抽 b」**只有结构断言抓得住**。

### 11.5 如实保留的红项与缺口

- **红项**：欢乐颂第 4、8 小节应为句尾半终止（`G`），引擎配 `C` / `Dm`——**A2 尚未实现**，评测集把它变成了可复现的靶子
- **标注修订记录**：小星星 5/7 小节补入 `G7`（旋律含 `4` = G7 七音，教学配法通行；初稿漏写）。修订发生在看到输出之后，已写进语料的 `revisions` 字段
- **最大缺口**：**小调传统曲目 0 首**，小调项全是自制片段 ⇒「小调 100%」只能当回归闸，**不能当作小调达到专业水准的证据**

**下一步**：A2 句尾终止式（靶子已就位）→ 补齐传统小调民歌语料 → P1 难度引擎（五级）。

## 十二、套路库扩充（v60.17）：从 free-midi-chords 导入

### 12.1 先回答「够不够」

**不够，且缺口有实测证据**。用评测语料逐段审计，未命中的段落走的是
`V7-I-V7-I`、`I-I-V-I`、`I-V7-I-V` 这类**主属交替**——12 条手写套路里一条都没有，大调命中率只有 20%。

### 12.2 来源评估

| 项 | 结论 |
|---|---|
| 许可 | **MIT**（Copyright (c) 2019 Ludovic Drolez），可商用，保留署名即可 |
| 关键优势 | 进行表在源码 `chords.py` 里就是**级数文本 + 情绪标签**，**不必解析 MIDI、不必分发其文件** |
| 规模 | 大调 50 + 小调 58 + modal 约 30 |
| 取用范围 | 只取「级数序列」这一层；modal 表整表未用（♭II/♭III/♭VI/♭VII 我们在大调语境下没有候选） |

### 12.3 导入不是照单全收：三道过滤都是被实测逼出来的

| 过滤 | 例子 | 为什么必须 |
|---|---|---|
| **表达不了则整条丢弃** | `I IV vii iii vi ii V I` | 不做「删掉一格再凑」——那会改掉进行本身 |
| **退化项** | `I I7 Idom7 I7` → `I-I-I-I` | 不是进行，是静态主和弦；入库只会虚增命中率 |
| **准退化项**（单一和弦占比 ≥3/4） | `I I7 Idom7 IV` → `I-I-I-IV` | 音乐内容原在七/加音色彩上、那层我们表达不了；实测把 `tv_arrange` T13 末小节从 `Am` 掰成 `F` |
| **截断护栏**（引擎侧） | 8 格套路截成 4 格 = `I-I-I-I` | 同样是拿静态主和弦冒充命中（两只老虎实测中招） |

净增 **81 条**（大调 32 + 小调 49），套路库 12 → **94 条**。

### 12.4 导入库没有的，仍得自建

**主属交替族**（`1-5-1-5`）——流行向的进行库整族没有，但儿歌与传统民歌大量在用。
**不开旋转**：开了之后 `V-I-V-I` 相位会把属和弦放到乐句头上，实测把「玛丽有只小羊羔」从 8/8 打到 6/8。

> 这条印证了第九节的判断：**导入解决通用/流行向的覆盖，垂类（儿歌·教学·民歌）的内容仍是自建资产**——
> 与 B 系列节奏型库同一个结论。

### 12.5 试过但撤掉的（如实记录）

「逐小节让步上限」：任一格丢掉超过该小节最佳契合度的 40% 就作废整条模板。
实测**既没卡住目标案例**（两只老虎那处 `G7` 只比 `C` 差 12%，卡不住），
**又误伤了正确命中**（铃儿响叮当那条逐格吻合的 8 小节套路被毙）。**已撤除。**

### 12.6 成绩与一个方法论教训

| 指标 | v60.16 | v60.17 |
|---|---|---|
| 级数准确率 | 97.5% | **98.8%** |
| 功能准确率 | 97.5% | **98.8%** |
| 套路命中率 | 40% | **60%**（大调 20% → 46.7%） |
| 剩余红项 | 2 | **1**（欢乐颂 m4 句尾半终止 = A2） |

**教训：聚合数字会骗人。** 加主属交替族后总分停在 97.5% 没动，看着像没影响；
逐曲一看才发现是**一换一**——欢乐颂 m8 修好了，两只老虎 m3 却被掰成 `G7`（同一条旋律的 m4 却配 `C`）。
**必须逐曲看，不能只看总分。**

v60.17 说明里的「原表 108 条」只是前两张表，**modal 82 条被整表跳过且未在对外说明里记账**。

**更正后的完整账（190 条）**

| 去向 | 条数 |
|---|---|
| 已导入 | **83**（大调 32 + 小调 49 + modal 回收 2） |

| 退化 / 准退化 / 长度剔除 | 5 |

**modal 表不是「不能用」，是「需要新增候选级数」。** 按主音语境重新分流后：

| 语境 | 条数 | 现状可表达 | 补 ♭III/♭VI/♭VII/iv | 再补 ♭II | 再补 IV/I |
|---|---|---|---|---|---|
| 大调语境 | 45 | 0 | **27** | 34 | — |
| 小调语境 | 37 | **4** | — | 18 | **30** |

> 小调语境里的 `♭III/♭VI/♭VII` **本来就等于**本项目小调候选的 `III/VI/VII`——
> 有 4 条现在就能表达（去重后净增 2，已入库）。**这是整表跳过造成的实际漏收，不只是口径问题。**

**下一项：借用和弦（同主音小调借用 ♭III/♭VI/♭VII/iv + ♭II）**
再补 5 个候选级数可回收 52 条以上，覆盖 190 里的 160。
但这是**候选集的能力缺口**而非「多加几条模板」——`C-B♭-F` 这类走向在流行/摇滚/影视/古风里极常见，

## 十三、AccoMontage2 评估（钢琴伴奏方向）

评估对象：`billyblu2000/AccoMontage2`（arXiv 2209.00353）。结论先行：
**代码与数据不引入；架构验证了我们已走的路；有三点纯规则的做法值得立刻借鉴。**

### 13.1 核对到的事实

| 项 | 实测 |
|---|---|
| 许可 | **MIT**（Copyright (c) 2021 Billy Yi） |
| 仓库自带数据 | ~236MB：`dict.pcls001/2/3`(124MB)、`source_base.pnt`(53MB)、`new_source_base.pnt`(37MB)、`representatives.pcls`、`transition_score.mdch`、另有 21MB 的 `default_sound_font.sf2` |
| 织体模块 | **PyTorch 神经网络**（`models/ptvae.py` 的 `PtvaeDecoder`）——反序列化时的导入链暴露的 |
| 预训练权重 | **不在仓库里**，README 要求另从网盘下载 |
| 运行栈 | Python + pandas + torch + pretty_midi（本地试读它的进行字典，因缺这套栈而失败） |
| 上游数据 | 伴奏片段库源自 **POP909**（该仓库亦为 MIT）；进行库称源自 **Niko 数据集** |
| 风格标签 | `progression-style`: emotional / pop / dark / r&b / edm / unknown；`style`: pop_standard / pop_complex / dark / r&b |

### 13.2 为什么不引入

1. **形态冲突**：织体模块是神经网络 + 需另下权重 + 整套 Python 流水线，
   与「单文件 · 无构建 · 浏览器内运行」的硬约束正面冲突。要用只能做**服务端功能**——
   那是产品形态的决定，与已拍板的「音频转 MIDI 暂不做」同类，需先拍板而非顺手引入。
2. **底层版权风险（这条最关键）**：POP909 仓库虽是 MIT，但它是 **909 首商业中文流行歌的扒谱**；
   **仓库许可清洗不了底层音乐作品的著作权**。AccoMontage 的做法是**从真实伴奏片段库检索并拼接**，
   输出会带原编曲的形态特征。对一个面向中国市场的**商业**制谱产品，不建议把 `source_base.pnt` 当伴奏素材源。
3. **数字未经复核**：README 与论文页称「5k+ 进行、四种风格标签、源自 Niko 数据集」，
   但**我没能在本地核实**（读字典需立起 pandas+torch+pretty_midi），
   **Niko 数据集本身的许可我也没查到明确声明**。「5k+」目前只是**转述，未经复核**。

### 13.3 架构上的相互印证

他们的和声模块 = 进行模板库 + `transition_score.mdch` + `DP.py` 的动态规划，
**与我们 v60.15 的 A8（模板 × 乐句跨度 DP）是同一套结构**。
这不是巧合——它是这个问题的正解形态。我们的路子走对了。

### 13.4 值得立刻借鉴的三点（纯规则、零依赖）

| # | 借鉴点 | 我们的现状 | 价值 |
|---|---|---|---|
| **T1** | **乐句级织体选择**：按乐句选伴奏、主歌副歌换织体 | `arrangeAccompaniment(texId)` **整曲一个织体** | 「像不像成品」的最大短板；A3 切句已就位，改动集中 |

### 13.5 我们自己的钢琴伴奏家底（对照）

## 十四、钢琴伴奏织体扩充（v60.19）：从 POP909 采「节奏骨架」

### 14.1 采哪一层，以及为什么这一层是安全的

POP909（MIT · Copyright (c) 2020 Music X Lab）是 **909 首商业中文流行歌的扒谱**。
仓库许可解决的是「这份标注数据可以用」，**清洗不了底层音乐作品的著作权**。
因此只采「不构成表达」的那一层：

| 采 | 不采 |
|---|---|
| 左右手在**拍位**上的起音分布 | 任何音高内容（音符 / 音程 / 和弦） |
| 右手是**柱式**还是**分解** | 任何具体乐句、任何曲目标识 |
| **跨曲频次**（被多少首不同的歌共用） | 只出现在个位数曲目里的骨架 |

被两三百首歌共用的打法是**体裁惯例**（「低音走八分、和弦落在二四拍」），不是任何一首歌的表达。
落地时由人按我们自己的 `PIANO_TEX` 惯例**重写**成模板，音级（1/3/5/8）本就由和弦决定。

> **采的是「中文流行钢琴伴奏一般怎么打节奏」这个事实，不是任何一首歌怎么弹。**

### 14.2 统计口径调了两轮才站得住

| 口径 | 结果 |
|---|---|
| 16 分格逐格比对 | 1956 种骨架，**没有一种过 20 首的闸**——被演奏细节打散 |
| 8 分格 | 1584 种，且前 12 名里 5 条其实是「左手八分但缺一格」的**同一织体** |
| **按拍位类别归并**（哪几拍有音 + 有无后半拍） | 站得住：**908 首 / 72191 小节**，过闸（≥90 首）**63 种**，覆盖 48.6% 小节 |

工具：`deploy/pop909-texture.py`（零依赖最小 SMF 解析；用 `set_tempo` 建 tick↔秒 映射后
按 `beat_midi.txt` 的重拍定小节线，不假设「从 0 起每 4 拍一小节」）。

### 14.3 补进来的 6 套（括号=共用曲目数）

| 织体 | 共用曲目 | 难度 | 此前有无 |
|---|---|---|---|
| 抒情长音（每小节一次） | 212 | 入门 | 无（4/4 无长音型） |
| 左手流动＋右手柱式 | 352 | 初级 | 无（原 arp8 右手是单音） |
| 低音走三拍＋和弦 | 233 | 初级 | 无 |
| 仅左手流动（间奏／留白） | 186 | 初级 | 无 |
| 反拍和弦（右手只落二四拍） | 231 | 中级 | 无 |
| 密集柱式推进（副歌） | 383 | 中级 | 无 |

原有 11 套 4/4 偏抒情与古典，**缺的正是流行伴奏的高密度推进型、反拍型与留白型**。织体库 15 → **21 套**。

### 14.4 难度改五级，并踩到一个真回退

难度从 入门/进阶 两档改为已拍板的**五级**。改完立刻踩坑：
两个织体弹窗把难度组**写死成** `['入门','进阶']`，改五级后初级/中级/高级三组直接不渲染，
4/4 可选项从 15 掉到 **3**——被 `tv_acc` T7 当场抓住。已抽出共用的 `TEX_LV` 常量。

### 14.5 测试改成跟着库走

原来三处断言钉死数字（「共 15 套」「弹窗 9 套」），每加一套织体就得改一次。
现改为**与 `PIANO_TEX` 实际条数一致**，并新增**结构性不变量**：
每套织体左右手的时值和必须等于它声明的拍数（6/8 按 `unit=8` 折算，与生成器同口径）。
写坏一套模板立刻转红——比数数有用得多。

### 14.6 仍缺

- **专业级织体 0 套**（现有最难是十六分全分解＝高级）
- 伴奏仍是**整曲一个织体**——乐句级织体选择与段落对比（第十三节的 T1）是下一项
