# 谱库与新建：分类升级方案（2026-11）

> 2026-10-31 · 只出方案，未改产品代码 · 待负责人拍板（§8）· 已按三类用户（中学音乐老师 / 弹唱爱好者 / 合唱指挥）＋工程视角评审一轮，改动逐条见 §九
> 负责人原话（2026-10-31）：「曲谱与谱库的分类我认为需要优化，无论是曲谱分类还是曲谱新建我认为要以用户需求作为优先级，结合网站的核心功能升级分类。」
> 依据：内部盘点（四套分类口径，编辑器 docType、服务端 docTypeOf、统一谱名逐例对拍）＋外部调研（UG、Musicnotes、J.W. Pepper、MuseScore、Dorico、Sibelius、GP8、Flat 和国内谱站 App 介绍。外网多数页面本环境打不开，只用到搜索摘要，没有逐页核对）。

---

## 一、结论

**推荐：方案 A「按用途找谱、按用途建谱」做主轴，再吸收方案 B 的长处，把「乐器」做成第一个分面，同时做第二条 SEO 轴。**

1. **一级 8 个词，与新建用途一一对应。** 谱库一级：**弹唱 · 钢琴伴奏 · 歌谱合唱 · 教学对照 · 视唱练耳 · 指弹独奏 · 器乐 · 和弦谱**。v37.3 的「八场景」升级成「八用途」：仍是 8 个，名字改成用户自己的说法，排序和新建面板一致。新建卡名（如「钢琴即兴伴奏」「儿歌弹唱」）不强改，对应关系写死在 `CATS.intent` 里，并在发布对话框显示「将归入：钢琴伴奏 › 伴奏歌谱」（评审 R1）。
   - 「弹唱」一级只装吉他 / 尤克里里，但师范、考编说的「弹唱」常指钢琴自弹自唱（shifan 页标题就是「师范生弹唱、儿歌伴奏」）。所以「弹唱」二级末尾放一个跳转钮「钢琴弹唱 ›」直达「钢琴伴奏」，搜「钢琴弹唱 / 儿歌弹唱 / 自弹自唱」也落到钢琴伴奏（评审 R1）。
2. **记谱法不当分类，当能力展示。** 卡片加角标「简⇄五」，观看页一键切换（v69.6 已有「简谱 / 五线 / 对照」）。三记谱法同源互切这条护城河，用户找谱时就能看到。**一级分类不随旋律用简谱还是五线谱而变**（评审 R3，金表断言「互切不变」）；搜「简谱 / 五线谱」只决定打开时怎么看，不当硬筛选。
3. **乐器、编制、能力、调拍速做分面；场景做专题。**
   - 能力分面只留两个：已配和弦、带伴奏。「带伴奏」同时以开关的形式出现在「歌谱合唱」「器乐」的二级行末，全站只用这一个叫法（评审 R4）。「可出分谱」不做筛选，只做卡片小标「分谱」，且只给合唱 / 重奏 / 多把吉他（评审 R6）。
   - **儿歌是风格，不是谱的形态**：跨类的「儿歌」标记，弹唱、钢琴伴奏、歌谱里都能有（评审 R8）。
   - 专题对应考编、艺考、师范、即兴伴奏。现有 4 个垂类页改成「专题说明＋预先筛好的谱库＋一键开建」。专题的筛选是并集，不等于某个一级：例如「考编即兴伴奏」＝钢琴伴奏 ∪ 带和弦的单旋律（评审 R2）。
4. **数据不改名。**
   - 新分类全部从现有字段推断。新函数 `catOf` / `facetsOf` 放进 `PQ_KIND`，编辑器和 `api/kindname.js` 两处逐字节同一份。
   - 旧的 `type` 字段和 docType 原样保留，供老客户端、封面配色、调号写法使用。
   - 唯一新写入的字段是新建时的可选 `song.intent`，缺省时按谱面推断。
5. **顺手修掉现有的不一致：**
   - 同一个用途建出的谱落进不同筛选；
   - 曲库 9 首艺术歌曲落在「器乐五线 / 钢琴独奏」，卡片却叫「钢琴伴奏歌谱」；
   - 尤克里里独奏不进「尤克里里」；
   - 服务端 docTypeOf 和编辑器判法已经分家（v69.6 I6 只改了一边）。

**分 5 段上线（P0–P4）**，每段都能单独上线、单独回滚。P0＋P1 合起来约一个版本，做完谱库就换成新分类。需要拍板 16 项（§8），最关键的 5 项：主轴选 A；八用途名单；「钢琴弹唱」的词义；docTypeOf 收进 PQ_KIND；人声＋钢琴交叉收录（第 14 项）。

## 二、现状的问题（为什么要改）

1. **四套口径各说各话。**
   - 新建用的是 11 个用途（`NWP.SC`，index.html:38017–38028）。
   - 谱行组合有 14 种，统一谱名约 25 种（`PQ_KIND`）。
   - 谱库筛选用 10 个 docType（`CC_CATS` index.html:45501、官网 `CATS` site/index.html:61–62）。
   - 官网有 4 个垂类页。

   新建里的「儿歌弹唱、视唱练耳、钢琴即兴伴奏」在谱库里找不到；谱库的「钢琴独奏、器乐五线」在新建里也没有。
2. **同一个用途建出的谱，落进不同筛选**（脚本实测，见 §6.4）：
   - 「钢琴即兴伴奏」用简谱旋律建，落「歌谱」；用五线谱建，落「器乐五线」；选纯伴奏，落「钢琴弹唱」。
   - 二胡简谱落「歌谱」。
   - 尤克里里独奏落「独奏」，不进「尤克里里」。
   - 同样叫「五线谱重奏谱」：新建的落「歌谱」，导入的落「器乐五线」。
3. **曲库名实不符。** 8 首艺术歌曲在筛选里是「器乐五线」，《阿特拉斯》是「钢琴独奏」，卡片上却都叫「钢琴伴奏歌谱（五线谱）」。PROJECT.md:530 一直挂着待拍板。
4. **筛选维度混杂又缺项。** 11 个按钮里混了四种维度：用途（教学对照）、乐器（尤克里里）、记谱法（器乐五线）、谱的形态（和弦谱）。同时没有按乐器、按编制、按能力的筛选；用户说的「XX 吉他谱 / 二胡谱 / 简谱」也没法直接变成筛选。
5. **工程上的缺口。**
   - 分类只在前端过滤，接口不带关键词时只返回最新 200 首（db.js:243–247），第 201 首以后按分类筛不到。
   - 服务端 `isChoirOf/docTypeOf`（server.js:241–263）是 PQ_KIND 之外的另一份拷贝，已经和编辑器判法分家。
   - 用户新建时选的用途不进 song，刷新就丢。
   - 后台看不到 `create_stack` 按用途的分布，拍板 10「上线后校准默认用途」因此一直没法执行。
   - 分类没有落地页，sitemap 是平铺的。

## 三、方案 A：以用途场景为主轴（乐器 / 记谱法 / 编制 / 能力为分面）

**思路**：按「我要干什么」分。一级 = 8 个用途，与新建面板同名同序；乐器、编制、能力、调拍速做分面；考编、艺考、师范、即兴伴奏做专题（预设好的筛选组合＋说明＋一键开建）。

### 3.1 谱库筛选长什么样

```
[ 搜索：曲名 / 歌手 / 作曲（输入「成都 吉他谱」→ 搜索框下出现可删的条件块「乐器：吉他 ×」，曲名按「成都」搜） ]
一级：全部 | 弹唱 | 钢琴伴奏 | 歌谱合唱 | 教学对照 | 视唱练耳 | 指弹独奏 | 器乐 | 和弦谱 | ♥ 收藏
二级（选了一级才出现，占用同一行）：例 钢琴伴奏 → 伴奏歌谱 · 纯伴奏 · 合唱伴奏 ｜ 考编专题 ›
                                   例 歌谱合唱 → 独唱 · 合唱 ｜ [带伴奏] 开关
                                   例 弹唱     → 吉他 · 尤克里里 ｜ 钢琴弹唱 ›
乐器（电脑常显一行，多选）：吉他 · 尤克里里 · 钢琴 · 人声 · 西洋管弦 · 民乐 · 键盘
[筛选 ▾] 抽屉（多选，结果数随选项变化，「清空」一键）：
  风格：儿歌（P2 起读 intent，P4 起读标签）
  原稿记谱：简谱 · 五线谱 · 六线谱 · 和弦（旁注：带旋律的谱都能在观看页切成简谱或五线谱）
  编制：独唱 / 独奏 · 二声部 · 三声部 · 四声部以上
  能用来：已配和弦 · 带伴奏 · 多段歌词
  调（六线谱 / 四线谱按「指法调＋变调夹」显示，如「C调指法 · 夹2」）· 拍号（2/4 3/4 4/4 6/8）· 速度（慢 ≤72 / 中 / 快 ≥120）（旁注：都能一键移调）
排序：最新 · 最多收藏 · 最多浏览
卡片：统一谱名 + 角标「简⇄五」+ 能力小标（配和弦 / 伴奏 / 分谱）+ 调拍速小节数
```

- 一级和二级是单选，分面是多选。0 首的类别照旧不显示（改由服务端统计全库数量）；**例外**：钢琴伴奏、教学对照、视唱练耳这三个主攻类，以及「儿歌」风格，0 首也显示，空列表页给「用示例做一份 / 自己做一份」（评审 R9）。
- **原来设计的「专题」常显一行撤掉**：专题入口放进对应一级的二级行末（钢琴伴奏 →「考编专题 ›」，视唱练耳 →「艺考专题 ›」，教学对照 →「课堂专题 ›」，筛「儿歌」时 →「师范专题 ›」），另在首页搜索框下放一句文字链「考编 · 艺考 · 师范 · 即兴伴奏专题」。原因：两个专题和一级几乎重名（「艺考视唱」≈「视唱练耳」），常显一行等于同一个东西两个按钮，手机上又多占一行（评审 R5）。
- **手机与小程序（375px 宽）**：只常显「一级」一行（横滑），二级选中后替换同一行；乐器行、筛选抽屉合并成「筛选 ▾」底部弹层。验收要求：第一张卡片在首屏内（评审 R5）。
- 搜索解析出的条件一律显示为可删的条件块；解析后结果为 0 时，自动退回整句全文搜索（评审 R7）。
- 标签只在 P4 做，而且是可选的：风格（儿歌、民歌、流行、红歌、艺术歌曲、古典、影视、戏曲）和考试（考编、艺考、考级、课堂）。标签只用来做专题和 SEO，不当主分类。
- 难度只在 P4 做：先从谱面自动推出三档（入门 / 进阶 / 挑战），作者也可以选填。

### 3.2 新建入口第一步问什么

还是先问**「做什么谱？」**，即现有 9 个用途，加「空白谱」「自选记谱法」。面板骨架不动（v67.4 刚上线，拍板 3 / 8 的结论都保留），只做 5 件事：
1. **名字对齐（不强改卡名）。** 新建卡名保留用户的原话（「钢琴即兴伴奏」「儿歌弹唱」都是考编、师范的科目名），对应的谱库位置写在 `CATS.intent` 里：「钢琴即兴伴奏」→「钢琴伴奏 › 伴奏歌谱」，「儿歌弹唱」→「钢琴伴奏 › 伴奏歌谱」＋儿歌标记。用户在两处看到的词不完全相同，所以用两处补上关联（评审 R1）：
   - 发布对话框显示「将归入：钢琴伴奏 › 伴奏歌谱」；
   - 谱库「弹唱」二级行末放「钢琴弹唱 ›」跳转。

   〔考编〕〔师范〕〔课堂〕〔艺考〕〔乐队〕这些小标签保留，作为通往垂类的路标。
2. **记下用途。** 创建时写入可选字段 `song.intent`，用来在谱面推断有歧义时裁定归类（§6.3）。「换谱类」（v67.5）也算重新选用途，同时改写 intent（评审 R10）。
3. **补 4 个用户要、现在拼不出的组合：**
   - 歌谱·合唱 加「钢琴伴奏」（复核 N8「拼不出合唱＋钢琴」）。中小学、社区合唱团多用简谱，所以**简谱合唱＋钢琴**的刻版验证列为 P2 的明确任务，不再写「验证后再开」（评审 R11）；
   - 指弹 加「尤克里里」；
   - 器乐独奏 加「钢琴伴奏」（如小提琴＋钢琴，艺考器乐常用）。P2 只开**五线谱旋律**（谱行 SG）。民乐简谱＋钢琴会落到谱行 JG，谱名是「钢琴伴奏歌谱」，名实不符，等 §8 第 16 项拍板后再开（评审 R3）；
   - 视唱练耳 加「简谱」（师范、幼师的视唱常用简谱）。
4. **用数据定排序。** 首访默认仍是吉他弹唱（拍板 10）。P0 补上后台按用途的统计，两周后按 `create_stack` 和谱库点击重排。
5. **谱库通到新建。** 分类页、零结果页、专题页的「没找到？自己做一份」按钮都带上 `?new=<对应用途>`，让「找不到」直接变成「建一份」。手机不能新建（拍板 1），所以在手机和小程序里，这个按钮改叫「发到电脑做」，打开编辑器的「在电脑上开始一份谱」页并预选该用途。小程序 web-view 里，如果 zhipu 子域没配成业务域名（`miniprogram/README.md:65` 写的是「可选」），这个按钮用 `mp-hide` 隐藏，免得点了打不开（评审 R5）。

### 3.3 谱名表（PQ_KIND）怎么变

- **新增，只读推断，不写字段：**
  - `CATS`：8 个用途的 id、名字、slug、二级、对应的新建用途；
  - `INST_FAM`：22 种 instKey 到乐器族的对照，与 `NW_INSTS.fam` 一致，由 tv_kindsync 逐项核对；
  - `catOf(s)`，返回 `{cat, sub, also, kids}`（`also` 是交叉收录的另一个 `cat›sub`，只有人声＋钢琴两种情况有值）；
  - `facetsOf(s)`，返回乐器族、原稿记谱、声部数、是否带钢琴、是否有和弦、是否有伴奏、是否合奏（卡片「分谱」小标）、实际歌词段数、指法调。
- **收编**：把编辑器 `docType()`（index.html:37108–37119）的判法原样搬进来，叫 `docTypeOf`。编辑器 `docType()` 改为调用它；服务端删掉自己那份 `isChoirOf/docTypeOf`，也调用它。从此 `type` 只有一份判法，v69.6 的分家随之消失。
  - 搬进来时要改成防脏写法：编辑器原版直接读 `s.tabVoices.length`，没有兜底（index.html:37111），服务端的坏谱会抛错。
  - 服务端的 type、typeLabel、cat、fx 四个值都从**同一份清洗＋migrate 后的副本**算（即现在 typeLabelOf 用的那份），并且都包在 `safe()` 里。现在 `type` 读的是原始 JSON（server.js:302），typeLabel 读的是清洗后的副本，两边口径本来就不同。§6.9 第 5 条因此多一类漂移（评审 R12）。
- **谱名**（kindName）只有两处需要拍板的小改：
  - 合唱带钢琴大谱表时，叫「五线谱合唱谱（含钢琴伴奏）」或「简谱合唱谱（含钢琴伴奏）」；
  - 纯伴奏 CG 的谱名是否从「钢琴弹唱谱（纯伴奏）」改成「钢琴伴奏谱（纯伴奏）」（§8 第 3 项）。

  其余谱名逐字不变。
- 两处逐字节同一份，由 `deploy/check-syntax.js`、`api/kindname.test.js`、`tv_kindsync` 三处核对，机制不变。

## 四、方案 B：以乐器编制为主轴（场景为专题）

**思路**：按「什么乐器、谁来演」分，和 MuseScore 4（先选乐器）、GP8（先加音轨）、UG（按乐器分）的习惯一致；国内用户的搜索词也多是「曲名＋乐器＋谱」。场景只做专题。

### 4.1 谱库筛选长什么样

```
一级（乐器 / 编制）：全部 | 吉他 | 尤克里里 | 钢琴 | 声乐合唱 | 西洋器乐 | 民乐 | 乐队和弦
二级（谱的形态）：
  吉他 → 弹唱 · 指弹 · 六线谱           尤克里里 → 弹唱 · 指弹
  钢琴 → 独奏 · 伴奏歌谱 · 纯伴奏 · 对照含伴奏
  声乐合唱 → 简谱歌谱 · 五线谱歌谱 · 合唱 · 教学对照 · 视唱
  西洋器乐 → 小提琴 · 长笛 · 萨克斯 · 小号 · 圆号 · 长号 · 贝斯 · 重奏
  民乐 → 二胡 · 古筝 · 笛子 · 葫芦丝 · 唢呐 · 琵琶 · 扬琴 · 口琴
  乐队和弦 → 和弦谱 · 功能谱
专题（场景，策展加标签）：考编即兴伴奏 · 师范儿歌弹唱 · 艺考视唱 · 课堂对照 · 乐队排练
分面：原稿记谱 / 能用来 / 调拍速 —— 与方案 A 相同
```

### 4.2 新建入口第一步问什么

先问**「什么乐器 / 谁来演？」**，给 7 块：吉他、尤克里里、钢琴、人声·合唱、西洋器乐、民乐、乐队·和弦。第二步问**「做成什么谱？」**，只列这个乐器能做的形态，例如钢琴：即兴伴奏〔考编〕/ 儿歌弹唱〔师范〕/ 独奏 / 教学对照含伴奏。第三步是调、拍、速度、曲名。新建面板的 `GROUPS` 要改成按乐器分组，9 个用途挂到两层下面；用途 id 不变，深链 `?new=` 照常可用。

### 4.3 谱名表（PQ_KIND）怎么变

新增 `INST_FAM`、`famOf(s)`（一级乐器）、`formOf(s)`（二级形态）；docTypeOf 同样收编；场景只靠标签（`song.tags`，P4），没有标签就进不了专题，只能人工策展。kindName 不变。

### 4.4 官网 / 小程序 / SSR / sitemap

一级按乐器做按钮，URL 用 `?inst=piano&form=banzou`；SSR 页面是 `/pub/i/<instKey>` 和 `/pub/i/<instKey>/<form>`，正好对上「钢琴谱 / 吉他谱 / 二胡谱」这类搜索。4 个垂类页改成专题页，再加一个「乐队排练」专题。小程序同样不用改。

### 4.5 四个主攻垂类的路径

| 垂类 | 找谱 | 建谱 |
|---|---|---|
| 即兴伴奏 | 「钢琴」→「伴奏歌谱」→ 卡片：**3 步** | 「钢琴」→「即兴伴奏」→ 创建：**3 步** |
| 教师考编 | 专题 **2 步** | **3 步** |
| 艺考 | 「声乐合唱」→「视唱」→ 卡片：**3 步** | 「人声」→「视唱谱例」→ 创建：**3 步** |
| 师范 | 「钢琴」→「伴奏歌谱」→ 标签「儿歌」→ 卡片：**4 步**；专题 **2 步** | **3 步** |

### 4.6 核心功能露出

角标、能力分面、落地页「用它做…」与方案 A 相同。「配伴奏」只能出现在「钢琴」下面，不再是一级入口。

**优点**
- 器乐学习者（吉他、钢琴、二胡）1 步就到。
- 和国内「曲名＋乐器＋谱」的搜索习惯、和国外制谱软件的新建习惯一致。
- 民乐能被看见。

**缺点**
- 主攻垂类每条路径都多 1–2 步。
- 「教学对照」「视唱」被埋进「声乐合唱」，「配伴奏」退成二级。
- 和「八场景入口」原则（按我要干什么选）相反。
- 新建面板要改结构，v67.4 刚上线、刚重写过的 tv_newpanel / tv_deeplink / tv_shellflow 要大面积迁移。
- 专题依赖人工标签，冷启动时内容空。

## 五、对比与推荐

| 维度 | 方案 A 用途为主 | 方案 B 乐器为主 |
|---|---|---|
| 主攻垂类（考编、即兴伴奏、艺考、师范）找谱 / 建谱步数 | **2 / 2** | 2–4 / 3 |
| 器乐学习者找「X 谱」 | 乐器行 1 步（常显） | **一级 1 步** |
| 与新建面板一致 | **同名同序，几乎不改** | 要改结构 |

| 三记谱法、配伴奏露出 | **一级就有配伴奏，角标** | 配伴奏退成二级 |

**推荐 A，并吸收 B 的三样：**
1. 乐器做常显的第一分面；
2. SSR 乐器页 `/pub/i/<instKey>` 做第二条 SEO 轴；
3. 搜索词里的谱类词自动变成筛选，例如「X 吉他谱」「X 二胡谱」「X 简谱」。

这样既符合负责人说的「以用户需求为优先」（用户先想的是「我要干什么」），也接住了器乐用户和搜索流量。

## 九、评审记录（2026-10-31，三类用户＋工程视角挑刺）
